Example call

    Approved build Sealed machine Signed answer

    It's a check your agent runs before paying for a service: pay only if the answer was signed by the build the seller approved, running in hardware the seller can't tamper with.

    A seller runs their service in a sealed machine and approves that exact build on Celo. Your agent pays only when an answer comes back signed by that build, and anyone can check its payment on Celo later.

    1. The seller approves one exact build.

      They publish its fingerprint on Celo. From then on, buyers only pay for answers from a build the seller approved.

      release, measured as PCR0 to PCR2

    2. It runs in a sealed machine.

      A cloud computer its operator can't log into or change. AWS attests to exactly which build is running.

      AWS Nitro enclave, attestation

    3. Every answer comes back signed.

      The machine signs the request, the answer, the Celo data it read and the payment, all together.

      EIP-712 proof

    4. You pay only if the proof checks out.

      Your agent's payment permission moves no money by itself. The gateway uses it only after all four checks pass.

      x402 quote, EIP-3009 permission

    5. A tampered answer is caught.

      If the answer doesn't match what was signed, an honest gateway refuses to settle: the permission expires unused, and once Celo shows that, you're not charged. If the gateway itself changed it and settled anyway, you're charged, and the SDK reports it as paid but rejected, with a record that proves it.

      response_hash_mismatch, not_charged, paid_but_rejected

    Three ways a call can end

    These are the three outcomes in the demo, and what each one leaves on Celo. Celo shows a settled payment or an unused permission. Whether a call was verified takes the proof, which your agent checks.

    1. Verified and paid

      Every check passes, so the payment goes through. Celo shows the payment settled; your agent's SDK checks the proof itself, which is what makes the call verified.

    What this proves, and what it doesn't

    A proof records which code produced an answer. That's narrower than "the answer is right", and we say so. The security page lists the main limits and links to all of them.

    What a proof shows

    • Which approved build answered, for this request, with these inputs.
    • That it ran in a sealed machine, attested by AWS, with its key registered on Celo.
    • Which Celo data it used, read at a stated block and bound by hash. Re-reading that block is what checks the values, when your RPC still has it.
    • Which payment it answers for. The proof is signed before you pay and names your payment permission; whether that permission was used or expired unused is read from Celo, not from the proof. Anyone can read it there, given the payer's address and the permission's nonce. Both are in your pending ledger, pending.jsonl in the SDK's data folder, which the SDK writes before it sends a payment.

    What it doesn't show

    • That the answer is correct. A bad answer is a rules problem you can read in the source.
    • That the service is available. An operator can still withhold or delay answers.
    • That the build matches its source. That link is the owner's claim, shown as "Owner says it's built from github.com/… @ commit" until someone reproduces the build.
    • That requests are private. Request bodies are visible to the service's gateway and to the server the sealed machine runs on.
    • Protection when paying through buy. buy, Celo's marketplace of pay-per-call APIs, takes payment before the service runs, so Attessa can only check afterwards.
    • An instant "not charged". After a refusal, confirming it takes up to about two minutes, or you can cancel on chain for a little gas.
