A seller runs their service in a sealed machine and approves that exact build on Celo. A buyer pays only after the answer comes back signed by that build and the signature checks out. Here is each step, with the line the CLI prints for it.

Why it's needed, and who's involved

Without a check, you pay first. If the answer is wrong, you can't tell whether the code the seller stands behind ran, or whether the program was swapped or the answer changed on its way to you. Four parts make the check work.

Before any call

  1. Seller

    Runs a paid service inside a sealed machine and approves that exact build on Celo, from the wallet that owns their agent.

On every call

  1. Buyer

    You, or your agent. Asks for an answer and signs a payment permission. The Attessa CLI or SDK on your side checks every proof again on its own.

  2. Gateway

    Sits in front of the sealed machine and takes the payment, but settles only once the proof checks out against the registry on Celo. A marketplace such as buy would run it; in this demo the seller's side runs it too, one of our known limits.

  3. Sealed machine

    An AWS Nitro enclave. Its running code is measured, its operator can't log in or change it, and it signs every answer with a key that never leaves it.

Buyer's view

  1. 01

    You ask for an answer

    Your agent, or you, calls a paid API through Attessa instead of calling it directly.

  2. 02

    Attessa reads who is selling

    It looks the service up in the Attessa registry on Celo: which agent owns it (an on-chain identity, agent 412 here), which build the owner approved (a release, named by the build's fingerprint), and the source code the owner says it came from, which is their claim, not something Attessa checks. If the service isn't registered, it stops here and nothing is signed.

  3. 03

    It checks the sealed machine is answering

    A quick check that the registered machine is up at this address before anything is signed.

  4. 04

    You see the price and sign a payment permission

    The price arrives as an x402 quote. If it's within your limits (0.10 USDC a call by default, set by attessa init), you sign a permission to pay it, in USDC, or USA₮ on mainnet. Signing moves no money, and the permission expires in about 120 seconds.

  5. 05

    The gateway checks the proof, then you pay

    The sealed machine computes the answer from Celo data at a stated block and signs a proof that binds this request, this answer, those inputs and this payment to the approved build. The gateway checks it against the registry and only then settles. Attessa on your side, the CLI or the SDK, checks the same proof again on its own once the payment has settled, and records a failure as paid but rejected.

  6. 06

    You keep a record

    The answer and the evidence are saved locally. For 24 hours you can fetch the stored answer again from the gateway, with your wallet's signature. Anyone can check the payment on Celo, with no wallet and no payment.

  7. 07

    If the proof fails, nothing settles

    If any check fails (a tampered answer, a revoked build, a wrong signer), the gateway refuses before it settles, so it shouldn't use your permission. Attessa shows which check failed, waits for the permission to expire, and checks on Celo whether it was used: not charged if it wasn't, or settled_after_refusal if the gateway used it anyway. You can cancel it sooner, on chain, for a little gas.

Seller's view

  1. 01

    Register your agent

    Your agent's public identity is an ERC-8004 entry owned by your wallet. Everything else hangs off it. Coming. attessa agent register isn't built yet; the other five commands are.

  2. 02

    Build the sealed machine image

    On an AWS EC2 machine with Nitro enclaves turned on, in your service's repo at the commit you'll publish. The build packs your service into a sealed machine image and writes the three measurements, fingerprints of that image, that identify it.

  3. 03

    Approve that exact build on Celo

    An approved build is a release, identified by its measurements PCR0 to PCR2. Buyers see the source you name as your claim, not as something Attessa checked.

  4. 04

    Add your endpoint

    The endpoint is your service's web address and the address buyers pay, which is the gateway's. Buyers only pay the address you register here.

  5. 05

    Start the sealed machine

    It makes a fresh signing key inside, and AWS signs a report of exactly what is running.

  6. 06

    Register the signer

    The registry checks AWS's report on chain and records the machine's key as a signer for your approved build. From then on, anyone can check its proofs.

The records on Celo, and how they link

An agent owns an approved release. A signer is proven to run that release. An endpoint is where it sells and gets paid. A proof is checked against all of them.

  • Approved buildIn the code this is a release: the build's three measurements, approved by the agent's owner. Revoking it stops every signer that runs it within 60 seconds.
  • SignerThe key a sealed machine makes when it starts. It never leaves the machine. Every restart makes a new one.
  • ProofAn EIP-712 signature by the signer over the request, the answer, the inputs and the payment. AWS's report is the attestation; the proof is Attessa's.
