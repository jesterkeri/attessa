Contracts

Attessa deploys four contracts, all immutable. Two more are other people's registries that Attessa reads, and those can be upgraded by their owners. Ours are live on Celo Sepolia; our Celo mainnet addresses fill in once deployed.

ContractWhat it doesCelo SepoliaCelo mainnet
Attessa registryHolds approved builds, endpoints and signers. No admin key, and it can't be upgraded.After launch
Nitro validatorChecks AWS's attestation on chain each time a signer is registered or renewed. Built on base's nitro-validator.After launch
Certificate managerCaches AWS's certificates so registering a signer costs less.After launch
P-384 verifierVerifies the P-384 signatures in AWS's certificates for the two contracts above.After launch
ERC-8004 identity registryThe agent identity registry. Not ours, and upgradeable by whoever holds its keys.
Self Agent ID registryLinks a person-verified ID to an agent. Shown for information only, never part of the check. Not ours, and upgradeable.

A deploy check confirms that each of our four contracts' code on chain matches the compiled production build, and that they point at each other.

How changes are reviewed

Attacked first
An adversarial test writer tries to break the code with failing tests, in rounds. The rounds and what they found are logged in DONE.md.
Then a second model
A second model then reviews each task's diff. Its finished reviews are in the reviews folder.
No AI in the check
Whether a call is paid is decided by signatures, registry reads and re-reads of the Celo inputs alone.

The code and its review records are public: the reviews folder and DONE.md on GitHub.

Who holds which keys

  • The Attessa registry has no admin. Nobody can change its rules after deploy.
  • Each agent's owner approves and revokes that agent's builds and endpoints, from their own wallet.
  • The certificate manager's owner is a single offline key for now; a 2-of-3 Safe is planned. Its only power is revoking cached AWS certificates, which can block new signer registrations. Existing signers keep working, and it can't forge an attestation.
  • The signing key inside each sealed machine never leaves it. A restart makes a new one, which has to be registered again.

Known limits

  • A proof shows which approved build produced an answer. It doesn't show the answer is correct, or that the service is available.
  • The link from a build to its source code is the owner's claim until someone reproduces the build.
  • In the demo, the gateway is run by the seller's side, so its protection rests on the short payment window, cancel, the registered pay-to address, your own re-check, and the on-chain "not charged" confirmation.
  • Request bodies are visible to the gateway and to the server the sealed machine runs on.
  • Paying through buy has no payment protection: buy takes payment before the service runs.
  • Confirming "not charged" after a refusal takes up to about two minutes, or a little gas to cancel sooner.

All known limits, explained, or the full list with when each will be revisited in KNOWN-LIMITS.md on GitHub.
