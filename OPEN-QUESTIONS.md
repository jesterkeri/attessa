## From T03 (core) and T13 (enclave), 2026-10-30
Each was resolved with the smallest reading and pinned by a test or vector, so a ruling changes one place.
- [ ] **Frame size vs large payTo code (T13, likely to bite).** SPEC §4.2 caps messages at 65,536 bytes, but an evaluate reply carries `inputs` including payTo's code, base64-encoded: a 24,576-byte contract makes the reply ~67 KB. The enclave enforces the cap on incoming frames only. Rule needed: raise the reply cap, or bound the inputs.
- [ ] **Local-network IP literals (T03).** §2.1 "IPv4/IPv6 literals (except local)" read as: on `--network local`, IP literals are allowed over https; http only for `localhost:<port>`. `http://localhost` with no port (or `:80`, which WHATWG drops) is refused.
- [ ] **Empty host labels (T03).** §2.1 rejects only a trailing dot; WHATWG accepts `https://a..b` and `https://.example.com`, and so does core. No vector pins it.
- [ ] **Method case (T03 + T13).** core's `requestHash` uppercases the method (`post` == `POST`, pinned by a vector); the enclave rejects a lowercase method as `bad_frame`. Should the enclave accept lowercase?
- [ ] **`configure` reply (T13).** Unspecified; the enclave returns the same as `attest`: `{"attestation","signer"}`.
- [ ] **`rpcAllowedChains` (T13).** No stated purpose; validated as uint256 decimals and otherwise ignored.
- [ ] **How the enclave learns `releaseId` (T13).** Unspecified; it reads PCR0-2 via NSM `DescribePCR` at configure.
- [ ] **Deny list contents (T13).** Unspecified; ships `[]`, R2 tested with an injected list.
- [ ] **Error codes outside evaluate's list (T13).** Malformed messages map to `bad_frame`; bad body `bad_request`; bad inputs `bad_inputs`.
- [ ] **`source` capability-id grammar (T13).** Accepts `buy:<visible ASCII>` or `forno`.
- [ ] **NSM error after boot (T13).** Treated like boot: exit 3. `nsm_init` runs at process start, so a missing `/dev/nsm` exits before listening; SPEC lists the NSM step after configure.
- [ ] **Incoming frames need not be canonical JCS (T13).** Parsed strictly instead; every outgoing frame is exact JCS (tested).
- [ ] **Payer-sig hex case (T03).** §2.5 doesn't say; core requires lowercase hex, matching §2's lowercase rule.
- [ ] **Error for a null or wrong-length PCR in `registerSigner` (T04).** SPEC §3.4 step 4 requires PCR0-2 "non-null and each 48 bytes" but names only `DebugPcrs` (all-zero). The build uses `InvalidPcr` (approveRelease's error). Security-relevant: a 64 ‖ 32 ‖ 48 split concatenates to the same 144 bytes as an approved 48 ‖ 48 ‖ 48 release (`test_InvalidPcr_lengthShiftCollision`). Confirm `InvalidPcr` or name another error.
- [ ] **try/catch can't map two cases (T04).** A `selfRegistry`/identity registry address with no code, or a return that doesn't ABI-decode, reverts with empty data instead of `SelfLinkInvalid`/`NotOwner`. Both are fixed constructor args pointing at real contracts, so left as is.
- [ ] **Unicode version for UTS-46 is not pinned (T03 re-attack).** core uses tr46 5.1.1 (Unicode 16); Rust url 2.5.8 / idna 1.1.0 (ICU, Unicode 17) accepts code points added in Unicode 17 that TS refuses (e.g. U+1E6C0, U+10EC5, U+A7CE, U+11DD0, U+16EA0, U+10940). 19 of 2,130 fuzzed inputs differ, all from this; no input produced two different originHashes. SPEC §2.1 could pin the version (then the enclave refuses the same set).
- [ ] **JCS `-0` vector loses its sign in the file (T03 re-attack).** `JSON.stringify(-0)` writes `0`, so the Appendix B case never shows a Rust or Solidity runner a `-0`. Store it as raw bit patterns if it matters.
- [ ] **Registration gas headroom is thin (T07).** On the Sepolia fork with the production CertManager, `registerSigner` with base's real fixture projects to 14,547,623 gas for the whole transaction (21,000 base, calldata at 16 gas/byte, execution to `BindingMismatch`; MODEXP repriced per EIP-7883, +300 gas x 3,044 calls). That leaves about 1.45M under 16,000,000, and the success path adds about 4 storage writes. Celo Sepolia's actual MODEXP pricing was not checked. T16b measures the real number.
- [ ] **Local `http://localhost` with no port (T06).** `normalizeOrigin` rejects it (`not_https`), but the registry's on-chain check is only prefix plus length, so a local registry accepts it. Matches SPEC §2.1/§3.4 as written; flagging in case the spec meant the two to agree.
- [ ] **Plain `forge test` takes about 135 s (T05).** Invariants run at foundry's default depth 500 without the env vars from AGENTS.md. Adding `[invariant] runs = 256, depth = 50` to foundry.toml would match the AGENTS.md command; outside the current task.
- [ ] **SDK ledger fields beyond §7 (T20).** The pending ledger adds `code`, `signedAtBlock` (lower bound for log queries) and `settlementTx`; evidence rows allow null `amount`, `asset`, `payTo`, `agentId`, `requestHash` on rows stopped before a quote is read.
- [ ] **SDK error code choices (T20).** Inputs block hash or timestamp mismatch gives `inputs_mismatch`, only the age check gives `stale_inputs`; `expiresAt != issuedAt + 600` gives `proof_expired`; a malformed proof header gives `bad_signature`; an unreadable `.well-known` gives `origin_agent_mismatch`.
- [ ] **SDK daily cap accounting (T20).** Today's spend = every open reservation regardless of day + settled outcomes on the current UTC day.
- [ ] **`createAttestClient` second argument (T20).** Optional `registry`, `transport`, `fetch`, `sleep`, `now`, needed while deployments.ts has no registry address.
- [ ] **`sourceRef` lookup (T20).** Best effort `earliest..latest` getLogs; a public RPC may reject the range, then the field is empty.
- [ ] **Clean-clone typecheck needs core built first (T02 suspicion, confirmed in T20).** core's `types` points at dist. A source `types` export condition or project references would fix it.
- [ ] **40 s window vs idempotency (T19).** §6.2 step 3's window check would refuse a retry of an already-settled call; the gateway applies it to new payments only, repeats follow the step 4 table.
- [ ] **Replaying a stored 200 (T19).** The gateway requires the presented EIP-3009 signature to recover to the row's payer before replaying, so knowing the authorization fields is not enough. Smart-wallet (EIP-1271) buyers cannot pass this and must use `/v1/results`.
- [ ] **Liveness inside `accepted` (T19).** `accepted` must be JCS-equal to the quote except `extra.attestedExec.liveness`, which must be present and null or an object.
- [ ] **Gateway error mapping (T19).** Unreadable payload gives `payment_invalid{invalid_payload}`; a facilitator `/verify` error gives `payment_invalid{unexpected_verify_error}` with no row. Block hash or timestamp mismatch counts as `stale_inputs` (the SDK calls the same case `inputs_mismatch`, T20: the two should agree). An RPC failure at step 9 fails the check and nothing settles.
- [ ] **`created_block` (T19).** Head minus 20 blocks, so the log search cannot start after the authorization was used.
- [ ] **402 body and 202 PAYMENT-RESPONSE (T19).** 402 body is the PaymentRequired JSON; 202 PAYMENT-RESPONSE is `{success:false, errorReason:"settle_pending", transaction, ...}`.
- [ ] **Contracts not in SPEC (T19).** seller-host `/internal/evaluate` body `{requestId, method, path, body(base64), paymentId}`; facilitator auth header configurable, default `Authorization: Bearer`. T15 must match the first.
- [ ] **check-deploy compares runtime code and getters only (T10 adversary r3, unproven).** A deployer using custom initcode could leave production runtime code with storage already written (EnclaveRegistry records, CertManager verified certs) and still pass. SPEC §3.5 lists only code and wiring checks. Mitigation if wanted: replay the deploy txs' initcode against the compiled creation code, or read the creation tx input.
- [ ] **No end-to-end test for the .gitattributes export-subst attack (T10).** Fixed by reading blobs with `git cat-file` instead of `git archive`; the round-3 adversary showed the attack only at the archive step.
- [ ] **What `accepted` must hold for liveness (T19 + T20).** SPEC §6.2 does not say whether "offered" is the quote the buyer received (liveness object present) or what the gateway would offer on the paid request (no challenge header, so liveness null). T19's `matchAccepted` ignores liveness and accepts either; the SDK sends the object it was quoted. A strict stateless gateway would reject the SDK; sending null would break a gateway that caches its quote. Needs a SPEC ruling.
- [ ] **SDK: inputs block after the settlement block (T20 fix).** Ends `paid_but_rejected{inputs_mismatch}` without an RPC read; a failed read at or below the settlement block stays `uncertain{rpc_unavailable}`. SPEC is silent.
- [ ] **SDK: §10 code vs HTTP status (T20).** The SDK accepts a well-formed §10 body with a matching requestId without checking that the HTTP status matches that code's status. SPEC asks only for the body.
- [ ] **Unpaid rate limit vs unfunded authorizations (T19 fix round).** SPEC §6.1 counts only calls without PAYMENT-SIGNATURE against 120/min/IP. A probe sent 130 well-formed EIP-3009 authorizations from one IP, each signed by a fresh unfunded key; all 130 reached the facilitator's /verify (`insufficient_funds`), bounded only by the in-flight cap of 16. A junk header is refused before /verify. If /verify spends facilitator credits, this drains them. Proposal: count failed verifies against the per-IP limit. Code unchanged; needs a SPEC ruling.
- [ ] **Nonce used before the row's created_block (T19 fix round, breaks INV-11).** §6.3 searches AuthorizationUsed logs only from the row's creation block, and step 4 says "true, repeat next tick" with no limit. If /verify accepts a nonce that was already used (for example, the facilitator's RPC lags by 20+ blocks), the row stays `settle_pending` forever. Confirmed by a probe: still `settle_pending` 200 s past validBefore. Code unchanged; needs a SPEC ruling (for example, search from validAfter's block, or terminalize after expiry when authorizationState is true and no log is found).
- [ ] **§6.2 step order vs the idempotency table (T19 fix round).** Read literally, the 40 s window check runs before idempotency, so a repeat of a `too_late` payment (always under 40 s left) gets `authorization_window_too_short` and the table's `too_late` row is unreachable. The gateway follows the table for existing rows. Needs a ruling on which wins.
- [ ] **Empty userinfo in an origin (T03 fix round 3).** `https://@example.com` and `https://:@example.com`: WHATWG keeps no credentials, so core and Rust accept them; the oracle refuses. The oracle is only stricter and no originHash differs. SPEC §2.1 should say which reading it means.
- [ ] **Empty labels in an origin (T03 fix round 3).** `https://.com` normalises to `https://.com` in core and the oracle (valid WHATWG with VerifyDnsLength off). SPEC §2.1 could require non-empty labels.
- [ ] **No upper bound on Retry-After (T03 fix round 3).** Neither core's grammar nor the oracle caps it; the SDK should clamp the value it reads. SPEC §2.5 is silent.
- [ ] **`[1.0]` header reason (T06 fix round 2).** A non-canonical header text that is not an object is `not_jcs` in the Solidity adapter and the T06 adversary test, `field_grammar` in the T03 oracle. No vector covers it; SPEC §2.5 does not order the two reasons for non-objects.
- [ ] **node:sqlite ExperimentalWarning (T20 fix round 4).** The SDK's ledger lock uses node:sqlite (Node >= 22.13), which prints "ExperimentalWarning: SQLite is an experimental feature" once per process, so CLI users will see it. Suppress it in the CLI, or accept it? FLOWS §8 has no line for it.
